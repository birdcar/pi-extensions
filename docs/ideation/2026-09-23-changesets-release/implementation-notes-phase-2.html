Implementation Notes — Phase 2

Changesets Release Pipeline · 2026-09-23 · Swap Release Please for Changesets

Release Please removal — deletions left unstaged

Context
Spec step 1 says to git rm the seven files. The workflow engine's override requires every change to stay unstaged so the sibling reviewer sees the whole phase in git diff HEAD.
Decision
Deleted the seven files with plain rm. git diff HEAD shows each as a deletion, and all seven are listed in the phase's changed files so the commit stage can stage them by name (git add <path> records a removal).
Alternative
git rm, which stages the deletions and breaks the engine's unstaged-diff contract.

Workflow test — also removed Job.if and Step.if

Context
The spec lists the interface fields to delete as needs, Job.permissions, outputs, and workflow_dispatch. After the rewrite, nothing reads Job.if or Step.if either.
Decision
Deleted both, per the user rule to delete unused code completely. Kept Workflow.permissions (the CI test reads it), Step.name (read by step()), and the existing describe fixtures unchanged.
Alternative
Delete only the four fields the spec names.

Workflow test — neutral value in the token negative controls

Context
The old controls set every key to ${{ secrets.NPM_TOKEN }}. That value matches the rule's regex by itself, so the NODE_AUTH_TOKEN and _authToken controls would still pass if their regex branches were deleted (scout edge case 3).
Decision
Each control adds its key to the changesets step's env with the value "redacted", so each key has to be caught by its own branch of the regex. A scratch-copy mutation run also caught a token in another job's env, an _authToken written from a run step, an unpinned action in another job, a bypassed publish-script, a dropped aggregate verifier, and || true.
Alternative
Keep the old secret-expression value, which doesn't distinguish the three keys.

docs/releasing.md — bootstrap and gate wording checked against real behavior

Context
The spec's target says the bootstrap "runs bun run check" and should be re-run "whenever a package is added". Its error table says a docs-only PR "should not happen" to fail changeset status. In practice, the phase 1 script runs the check only before a publish and reads a fixed PACKAGES array, and Changesets treats any file under a package directory (README, tests) as a package change. The spec lets releasing.md's wording change as long as every fact stays.
Decision
The doc now says four things. The script publishes missing packages after bun run check passes. A new package has to be added to PACKAGES (after its dependencies) and the script re-run before that package's first release. CI fails a PR that touches any file in a package directory without a changeset, and bun changeset --empty covers package edits that shouldn't release. The prompts need a TTY, so scripts and agents pass flags instead (bun changeset --patch <pkg> -m "…"). Both non-interactive forms were tested here. AGENTS.md and README use the spec's text word for word, wrapped by prettier.
Alternative
The spec's text word for word, which gets the script and the gate's scope wrong.

Lockfile — the decision premise was off, and some packages were re-hoisted

Context
The spec says bun.lock "also has two legitimate https://github.com/ entries that must keep their URL". It had none; all 466 URLs pointed at the proxy.
Decision
Kept the host-specific hook, which still protects future git or tarball dependencies. After the swap, bun.lock holds no absolute URLs at all. Removing release-please moved agent-base 9.0.0, http-proxy-agent 9.1.0, and https-proxy-agent 9.1.0 up from nested @earendil-works/pi-ai entries, with identical integrity hashes. @changesets/cli pulled in picomatch 4.0.7 at the top level. No surviving entry was re-resolved. A replay showed bun add --ignore-scripts rewriting 348 entries back to proxy URLs, and the same add with the hook leaving 0.
Alternative
Not applicable (a surprise in the codebase, not a choice).

Verification — the frozen install survives changeset version

Context
The scout couldn't re-check that bun install --frozen-lockfile still passes after changeset version leaves bun.lock's workspace metadata at 0.1.0 (the risk behind the "no lockfile refresh" decision).
Decision
Checked it two ways. Probe 6, replayed with output visible: pi-services went to 1.0.0 and pi-write-for to 0.1.1 with ^1.0.0, the frozen install passed, and bun.lock didn't change. A go-live dry run with only publish-from-ci.md: both packages went to 0.1.1 with range ^0.1.1, the frozen install and the full bun run check passed, and the tarballs verified at 0.1.1. No lockfile refresh is needed, and the rejected --lockfile-only alternative stays rejected.
Alternative
Not applicable.
