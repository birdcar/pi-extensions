Bootstrap script — npm trust calls need a terminal for 2FA

Context
The spec captures the trust commands' output (out=$("${NPM_TRUST[@]}" list …)) and expects npm's "skip for 5 minutes" window to carry the remaining calls. In npm v11.20.0, otplease (lib/utils/auth.js:10-12) rethrows EOTP instead of prompting whenever stdin or stdout is not a TTY. A captured trust call can therefore never complete a 2FA challenge. It only succeeds inside a skip window that an earlier call with a terminal opened. On a re-run with nothing to publish (contract criterion 12), the first captured trust list would fail and show the y/N prompt for every package. With no skip window open, even an answer of y would fail at trust github.
Decision
trust github keeps its stdout on the terminal (saved as fd 3) and captures only stderr, which is where E409 appears. That way npm can ask for 2FA during the create call itself. trust list stays captured, because its output decides whether to skip. When it fails with EOTP and the script has a terminal, it runs once more attached to the terminal so npm can authenticate, and then it is read again. Every other list failure still goes to the y/N prompt. The playground's _2fa stub copies npm's TTY rule, and experiments 8–11 cover it. Mutation M5 (create output captured) breaks experiment 10, and M6 (no EOTP retry) breaks experiment 9.
Alternative
Rely on the skip window opened by the publish step, which is nicknisi's implicit behavior but breaks re-runs. Run the calls on a pty through script(1), which has platform-specific syntax and can't be driven in this sandbox. Create first and treat 409 as "configured", which contradicts the spec's list-first logic and experiment 2.

Bootstrap script — existence check reads the HTTP status, not curl -f

Context
The spec uses curl -sf -o /dev/null "${REGISTRY}${name/\//%2f}", and its playground has curl exit 22 on a 404. With -f, this machine's curl 8.7.1 exits 56 (not 22) on an HTTP/2 404. A DNS or network failure also becomes indistinguishable from "missing".
Decision
The script uses curl -s -o /dev/null -w '%{http_code}'. A 200 means the package exists and a 404 means it is missing. Anything else prints !! could not check <name> … and exits 1 before bun run check or any publish. A network blip can therefore never lead to a laptop publish of a newer local version (goal 1). The playground's curl stub reports the status the way real curl does: 000 with exit 6 when offline, and exit 22 only if -f were passed. Experiment 13 covers the unreachable case.
Alternative
Keep -sf and treat any non-zero exit as missing (the context map's fallback), which lets a network error fall through to npm publish.

Bootstrap script — replica-lag re-check on the version endpoint

Context
The spec says to "keep its replica-lag handling", but its error table says to re-check the package document after a failed publish. nicknisi's comment (reference script L29-32) names the package document as the endpoint that lags and the exact version endpoint as the one that "reads authoritatively".
Decision
The skip decision still reads the package document, so no second version is ever published from a laptop. The re-check after a failed npm publish reads ${REGISTRY}@birdcar%2f<pkg>/<version>, so a publish that did land is not reported as failed. Experiment 5a simulates a package document that is still lagging. Mutation M7 (re-check on the document) fails it.
Alternative
Re-check the package document as the error table says. That gives a false !! publish … failed while the replica lags, though re-running fixes it.

Bootstrap script — summary counts and small gap decisions

Context
The spec doesn't say what published= and trusted= count. It names gh auth status without a host and says only "before the first npm 2FA prompt" for the skip note.
Decision
published= lists packages whose npm publish succeeded in this run; a replica-lag recovery gets its own == line but isn't counted. trusted= lists publishers created in this run; a 409 is reported but not counted. A re-run therefore prints published=none; trusted=none; actions-prs=already enabled. The auth check is gh auth status --hostname github.com, so a stale token for another host doesn't block the script. The skip note prints once, after bun run check and right before the first publish, or before the first trust call when nothing is missing, so the check's output doesn't bury it. sleep 2 follows each publish and each trust create (nicknisi, and npm's bulk-usage docs). The y/N prompt accepts only y. A comment next to PACKAGES records the publish order and that new packages are added by hand. Both trust failure exits suggest npm login --registry=https://registry.npmjs.org/, since a token that bypasses 2FA passes whoami but can't manage trust.
Alternative
Count 409s and replica-lag recoveries as done. Use a bare gh auth status. Print the note before npm login, where it would scroll away during the 46-second check.

Bootstrap script — the spec's duplicate-publisher premise is contradicted by npm's docs

Context
The spec justifies the y/N prompt with "npm now allows several trusted-publisher configurations per package, so creating blindly could add duplicates". npm's docs at the pinned version (docs/lib/content/commands/npm-trust.md:44, v11.20.0) say "Currently, the registry only supports one configuration per package. If you attempt to create a new trust relationship when one already exists, it will result in an error."
Decision
The prompt is implemented as specified. It fires only when the list fails and does no harm. A blind create would most likely return 409, which the script already treats as "already configured".
Alternative
Drop the prompt and fall through to create, as nicknisi does. The spec didn't authorize that deviation.

Go-live — what this phase could not verify

Context
The playground stubs every networked tool, so a few real-world facts stay unchecked until the maintainer's run.
Decision
Four things are flagged for the go-live gate rather than changed:
  1. This session's permission classifier blocked even a --dry-run of npx --yes npm@11.20.0 trust github …. The pinned npm was never exercised, and nobody has confirmed the Socket Firewall serves it; it was published 2026-09-22. If it's blocked, move the pin to a release ≥ 11.15. The flags were checked against the v11.20.0 source (lib/commands/trust/github.js, lib/trust-cmd.js). REGISTRY keeps its trailing slash so npm's registryIsDefault check holds and the "may not support trusted publishing" warning stays off.
  2. When npm whoami fails, npm login re-serializes the user npm config file and drops its comments, including the Iru-managed Socket Firewall block markers. The registry= value survives. The script never reads or writes that file itself.
  3. Phase 2's releasing.md text says to re-run the script "whenever a package is added" and that it "runs bun run check". The script only covers PACKAGES and runs the check only when a package is missing, so phase 2's wording should match.
  4. bun run check leaves an untracked .pi-tests/ directory, because .pi-tests is only prettier-ignored. This predates the phase. I removed the copy my verification run created.
Alternative
None. These items need the maintainer's credentials or phase 2.
